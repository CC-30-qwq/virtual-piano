## 2. 命令行构建

### 2.1 坑一：`ELECTRON_RUN_AS_NODE` 会让 CocosCreator.exe 退化成纯 Node

如果 shell 环境里存在 `ELECTRON_RUN_AS_NODE=1`（从 VS Code 等宿主继承时会带进来），
Cocos 的可执行文件会被当成 `node` 运行，命令行参数解析全部失效，报：

```
CocosCreator.exe: bad option: --project
```

**必须用 `env -u ELECTRON_RUN_AS_NODE` 清除后再调用。**

### 2.2 坑二：Cocos 不读 `ANDROID_HOME`，只认构建配置里的路径

SDK / NDK 路径不在环境变量里找，也不完全依赖编辑器偏好设置，而是从
`packages.android.{sdkPath,ndkPath,javaHome}` 读。为空时构建报：

```
Error: 找不到 Android NDK/SDK 路径，请到 偏好设置 -> 外部程序 中设置
```

另外 `apiLevel` 默认值是 26，而本机只装了 34+，必须显式指定。

### 2.3 坑三：`--build "k=v"` 只能传顶层参数

`packageName` 这类嵌套参数（`packages.android.packageName`）用 `--build "packageName=xxx"` 传不进去 ——
它会落在顶层，校验器读不到，报 `packageName("") 校验失败，该选项为必填项`。

**必须用 `configPath` 指向完整配置文件。** 配置见 [build-configs/android.json](../build-configs/android.json)：

```json
{
  "platform": "android",
  "debug": true,
  "startScene": "<场景 uuid>",
  "packages": {
    "android": {
      "packageName": "com.virtualpiano.app",
      "sdkPath": "C:\\Users\\10258\\AppData\\Local\\Android\\Sdk",
      "ndkPath": "C:\\Users\\10258\\AppData\\Local\\Android\\Sdk\\ndk\\28.2.13676358",
      "javaHome": "D:\\jdk-17.0.20.1+1",
      "apiLevel": 36,
      "appABIs": ["arm64-v8a"],
      "orientation": { "portrait": false, "upsideDown": false,
                       "landscapeLeft": true, "landscapeRight": true }
    }
  }
}
```

### 2.4 完整命令

```bash
cd <project>
export JAVA_HOME="D:/jdk-17.0.20.1+1"
export PATH="$JAVA_HOME/bin:$PATH"

# 第一步：Cocos 构建，生成 build/android/proj 与 native/engine/<platform>
env -u ELECTRON_RUN_AS_NODE "D:/Cocos/editors/Creator/3.8.8/CocosCreator.exe" \
    --project "<project>" \
    --build "configPath=<project>/build-configs/android.json"
# 成功标志：build Task (android) Finished in (Ns)
# 注意：结尾可能出现 Electron 缓存报错与非零退出码，那是编辑器退出噪声，不是构建失败。

# 第二步：编译原生，产出 APK
cd build/android/proj
export ANDROID_HOME="C:/Users/10258/AppData/Local/Android/Sdk"
./gradlew assembleDebug
```

产物：`build/android/proj/build/virtual-piano/outputs/apk/debug/virtual-piano-debug.apk`（约 22MB）

### 2.5 坑四：Gradle 发行版下载被拦截

`services.gradle.org` 会 **307 重定向到 `github.com`**，在该网络环境下握手失败：

```
PKIX path building failed: unable to find valid certification path to requested target
```

特征很迷惑：`curl -I https://services.gradle.org/...` 能通（只看到 307，不跟随），
但 Java 跟随重定向后就挂 —— 因为拦截发生在 GitHub 那一跳。

**解法**：从镜像预置进 Gradle 缓存，一次即可，不改工程也不改全局配置。

```bash
DIR="C:/Users/<user>/.gradle/wrapper/dists/gradle-8.11.1-bin/<hash>"
mkdir -p "$DIR" && cd "$DIR"
curl -L -o gradle-8.11.1-bin.zip \
  https://mirrors.cloud.tencent.com/gradle/gradle-8.11.1-bin.zip
python -c "import zipfile;zipfile.ZipFile('gradle-8.11.1-bin.zip').extractall('.')"
touch gradle-8.11.1-bin.zip.ok      # 这个 .ok 标记是关键，缺了 wrapper 会重新下载
```

`<hash>` 是 wrapper 依据 distributionUrl 算出的目录名，首次失败时会自动建好，直接复用即可。

> 若后续 Maven 依赖（`google()` / `mavenCentral()`）也出现同类 TLS 问题，
> 用阿里云镜像替代仓库地址即可，同样是网络环境问题而非工程问题。

## 3. 验证自研代码是否真的被编译进去

```bash
python -c "
d = open('build/android/proj/build/virtual-piano/intermediates/cxx/Debug/<hash>/obj/arm64-v8a/libcocos.so','rb').read()
print('tag_count =', d.count(b'piano-engine-m0-skeleton'))
"
```

**不要用 `strings`** —— 本项目环境下 Git Bash 的 `strings` 对 `.so` 返回空，会造成假阴性。

正确的排查顺序：

1. 先确认 CMake 有没有收到源文件：构建日志里搜
   `CMakeFiles/cocos.dir/.../Classes/piano/PianoEngine.cpp.o`
   出现即说明 `native/engine/common/piano.cmake` 的 `include` 生效了。
2. 再用上面的 python 命令确认符号进了 `.so`。

## 4. minSdk 固定为 26

`native/engine/android/app/build.gradle` 里 `minSdkVersion` **写死 26**，不再读 `PROP_MIN_SDK_VERSION`
（模板默认值 21）。原因见《落地实施方案》M0-3 实施记录：原生音频走 AAudio，
而 `libaaudio.so` 只从 API 26 起提供，minSdk 为 21 会导致 `ANDROID_PLATFORM=android-21`、链接失败。

⚠️ **改 minSdk 的副作用**：CMake 的构建目录会换一个哈希
（`build/android/proj/build/Debug/<hash>/`），旧的整棵编译树不会自动删除。
实测每次切换约产生 2.9 GB 死数据，需要手工清理。

验证当前生效值：

```bash
grep ANDROID_PLATFORM build/android/proj/build/Debug/*/arm64-v8a/CMakeCache.txt
"$ANDROID_SDK/build-tools/36.0.0/aapt2.exe" dump badging <apk> | grep minSdkVersion
```
