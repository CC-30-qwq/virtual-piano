# 移动端横屏高仿真钢琴 — 技术方案（v0.2）

- 引擎：Cocos Creator 3.8.8
- 目标平台：**Android 单机**（不含 iOS；不依赖自建服务端）
- 音源：[Salamander Grand Piano V3](https://github.com/sfzinstruments/SalamanderGrandPiano)（Yamaha C5，CC BY 3.0）
- 保真目标：接近全量音源（16 力度层 / 48kHz / 立体声）
- 本期功能：自由弹奏键盘、音色与控制参数、MIDI 外接键盘输入

> **v0.2 变更**（据 v0.1 评审结论）：
>
> 1. 目标平台由「Android + iOS 双端」收窄为 **Android 单机** —— iOS 构建需 macOS，开发环境不具备，整条 iOS 线（AVAudioEngine 设备层、CoreMIDI、IPA 构建）移除。
> 2. 团队无原生音频开发经验 → 音频内核**优先采用 sfizz**，自研降为备选。
> 3. 不接受低音区循环感 → 低音区（A0–A2）改为**常驻 attack + 尾部磁盘流式**，保留完整自然衰减；中高音区仍用循环尾。
>
> 变更影响见 §11，风险重估见 §10。

---

## 1. 结论摘要

| 决策点 | 结论 |
|---|---|
| 音频后端 | **优先采用 sfizz**（开源 C++ SFZ 引擎，Android 侧由 Oboe/AAudio 承载输出）；验证不通过则自研 C++ 采样器内核。Cocos 内置音频层**不可用** |
| 跨语言调用 | 自定义 JSB 绑定 + **批量事件提交**，禁止用 `jsb.reflection.callStaticMethod` 传高频触键事件 |
| 内存策略 | 低音区：常驻 attack + **尾部磁盘流式**（完整衰减、无循环）；中高音区：常驻 `attack + 循环尾`；扩展力度层走磁盘 LRU |
| 采样率/位深 | 存储 48kHz / 16bit FLAC（24bit 作为可选档），运行时按设备输出采样率重采样 |
| 资源分发 | 全量音源（**~265MB**）随包或首次启动一次性导入，见 §11.2 第 1 项 |
| 手感核心 | **触摸/MIDI 时间戳对齐音频时钟 + lookahead 调度**，而非降低缓冲 |

M0 必须先验证的三件事：**目标机型实测延迟**、**sfizz 可行性**、**低音区流式尾部的实现路径**。任一不成立都要回到本文档改方案。

## 2. 音源分析

### 2.1 音源规格（已核实）

| 属性 | 值 |
|---|---|
| 乐器 | Yamaha C5 三角钢琴 |
| 录音 | 2× AKG C414，AB 制式，琴弦上方约 12cm |
| 格式 | 48kHz / 24bit FLAC（sfzinstruments 版），archive.org 原版为 WAV |
| 主音色 | **30 个根音**（小三度间隔，A0=21 … C8=108），**16 力度层**，共 480 条 |
| 锤击噪音 | `rel1`–`rel88`，**半音级**，1 层，note-off 触发 |
| 弦共振 | `harmS*` / `harmV3*`，小三度，3 层，note-off 触发 |
| 踏板噪音 | `pedalU1/U2`（抬）、`pedalD1/D2`（踩），共 4 条 |
| 调律 | Natural（keyswitch C0）/ Retuned（keyswitch C#0）两套 |
| 授权 | CC BY 3.0（可商用，**必须署名**） |

仓库结构：根目录 `Salamander Grand Piano V3.sfz` + `Samples/*.flac` + `Data/{region,vel_01..16,tune_nat,tune_ret,str_res,hammer,pedal}.txt`。

主音色命名 `{Note}{Octave}v{Layer}.flac`，如 `A0v1.flac`、`C8v16.flac`。

### 2.2 两个必须处理的坑

**坑一：Natural 版不是标准音高。** `Data/tune_nat.txt` 里每个根音有独立的音分修正值。若直接把整条采样当作标准音高使用，会有可闻音准偏差。

→ **本次选用 Retuned 版**（每个根音已单独校准到 12-TET），整条直接使用，预处理阶段不做任何变调。

**坑二：SFZ 大量使用 ARIA 扩展。** 原 SFZ 依赖 `#define` 宏、变量替换、`offset_oncc98` 等 ARIA 专有 opcode，只有 Plogue sforzando 能完整播放。

→ 预处理阶段把 SFZ **降级为引擎确定支持的子集**，或完全弃用 SFZ、改用自生成 manifest（见 §5）。

### 2.3 体积估算

### 实测数据（2026-09-28，已下载全部 641 个采样并逐个解析 STREAMINFO）

原始素材规格与预期一致：**48kHz / 24bit / 立体声**，641 个文件共 714 MB。

⚠️ **但时长比早期假设长约 2.7 倍**，这直接推翻了原先的体积估算：

| 音区 | 根音数 | 条数 | 早期假设 | **实测平均** | 实测最长 |
|---|---|---|---|---|---|
| A0–A2 | 9 | 144 | 8.5s | **21.76s** | 25.86s |
| C3–B4 | 8 | 128 | 5.5s | **15.15s** | 16.30s |
| C5–C8 | 13 | 208 | 2.5s | **7.32s** | 15.90s |
| **合计** | **30** | **480** | — | 10.62s（全样本均值） | 25.86s |

单条主音色原始 PCM：`48000 × 2ch × 2B = 187.5 KiB/s`。

按 §4.3 的分区策略（低音区存完整尾部、中高音区只存 attack + 循环段）重算：

| 音区 | 条数 | 存储内容 | 时长/条 | 合计 |
|---|---|---|---|---|
| A0–A2 | 144 | attack 4.0s + 完整尾部（流式） | 21.76s（实测） | 3133s |
| C3–B4 | 128 | attack 2.5s + 循环段 1.5s | 4.0s（裁剪后） | 512s |
| C5–C8 | 208 | attack 1.2s + 循环段 0.8s | 2.0s（裁剪后） | 416s |
| **合计** | **480** | | | **4061s** |

4061s × 187.5 KiB/s ≈ 743 MiB 未压缩，FLAC 按 55% 压缩率估 → **≈ 410 MB**。
再加 release 层与踏板噪音，**磁盘总量 ≈ 430 MB**（早期估算 265 MB 偏低）。

### ⚠️ 实测推翻：能量阈值裁剪几乎无效

`tools/audio-pipeline/analyze_decay.py` 对全部 480 个主音色做了衰减分析
（8kHz 单声道包络，门限取相对峰值的 dB）：

| 门限 | 低音削减 | 中音削减 | 高音削减 | 总削减 | 16bit PCM 体积 |
|---|---|---|---|---|---|
| −40 dB | 13% | 23% | 24% | **18%** | 1207 → 987 MB |
| −50 dB | 5% | 6% | 7% | 6% | 1140 MB |
| **−60 dB** | **2%** | **2%** | **2%** | **2%** | **1183 MB** |
| −70 dB | 1% | 1% | 1% | 1% | 1198 MB |

**结论：这些采样的尾部里没有多少「静音」，是真的响满那么久。**
低音区 21.76s 不是"衰减到不可闻之后的房间尾巴"，而是真实的琴弦余振。
即使把门限放宽到 −40 dB（已会损失可闻余韵），也只能省 18%。

**因此**：§5.1 里的「能量阈值裁剪」仍然保留，但它的定位要修正 ——
它是一个**安全步骤**（去掉文件末尾可能的数字静音），**不是体积优化手段**。
体积优化只能靠**循环**（中高音区）与**流式**（低音区尾部）。

**但这不意味着包体大。** M2-2 已实际跑通并产出音频包，实测结果远好于估算：

| 分段 | 个数 | 体积 | 占比 |
|---|---|---|---|
| **低音尾部 `_t`** | 144 | **71.1 MB** | 52.1% |
| attack `_a` | 480 | 45.2 MB | 33.1% |
| 循环段 `_l` | 336 | 12.9 MB | 9.5% |
| harm / rel / pedal | 161 | 7.3 MB | 5.3% |
| **合计** | **1121** | **136.4 MB** | |

**估算的 430 MB 是错的，实际只有 136 MB。** 错因是估算时假设 FLAC 压缩率约 55%，
实测是 **16.6%**（820 MB 原始 PCM → 136 MB）。压缩率之所以这么高：
降位深到 16bit 去掉了 24bit 的底噪，且循环段与低音尾部的电平本身很低
（−45 dB / −35 dB），熵极小。

**这直接推翻了一个权衡前提**：低音区不做循环的代价不是 240 MB，而是 **71 MB**。

**于是又往前走了一步：全区段取消循环。** 既然包体代价可控，就没有理由保留
任何循环 —— 循环会把衰减「冻结」在循环点上，之后只能靠引擎包络近似本应继续的
自然衰减，那是保真度上的妥协。

| 方案 | 包体 | 循环痕迹 |
|---|---|---|
| 中高音区循环 | 136 MB | 有 |
| **全区段无循环（已采用）** | **193 MB** | **无** |

**193 MB** 的实测值：480 个主音色全部输出完整自然衰减（`_a` 常驻段 + `_t` 流式段），
无任何循环。多花 57 MB 换掉全部循环痕迹。

> 这是「尽量仿真」原则的直接体现。且 193 MB 仍远低于 Google Play base 模块的
> 200 MB 上限 —— 音源甚至可以直接打进主包，不必走 asset pack。

**而全量解码进内存是 1.4GB 量级，绝对不可行。** 必须做"常驻 + 流式"的分段策略（§4.3）。

## 3. 延迟预算与手感

### 3.1 端到端延迟分解

| 环节 | Android（目标） |
|---|---|
| 触摸采样 → 应用事件 | 5–15ms |
| Cocos 事件 → 原生队列 | 1–3ms |
| 音频缓冲 | 5–10ms（AAudio Exclusive） |
| 输出到扬声器 | 5–10ms |
| **合计** | **20–40ms** |

真人钢琴家自身动作延迟即有 30–50ms，故上表在可演奏范围内。

### 3.2 关键设计：时间戳对齐

**手感的决定因素不是绝对延迟，而是音符之间的相对时序精度。**

方案：

1. 触屏事件携带系统时间戳（Android `MotionEvent.getEventTime()`，基于 `SystemClock.uptimeMillis()`）。
2. 原生层在音频流启动时建立「系统时钟 → 音频帧位置」的映射，并周期性用 `AAudioStream_getTimestamp` 校正漂移。
3. 事件入队时即换算为目标音频帧号，音频回调按帧号精确触发，而非"收到就发"。
4. 这使 UI 线程 10–30ms 的抖动**不传递到时序上**（抖动被吸收，仅影响绝对延迟）。

### 3.3 必做的验证（M0，P0）

写一个延迟测量页：点击屏幕同时发声，用户用麦克风回环录制，自动计算往返延迟。

- 覆盖机型：至少 3 台 Android（旗舰 / 中端 / 国产 ROM 各一）+ 1 台大屏平板（键盘布局验收用）。
- **若中端 Android 实测 > 60ms**：启用"延迟补偿"向导（用户手动校准滑块），并把该机型标记为降级体验。
- 若 Oboe Exclusive 模式在部分机型不稳定，回落 `SharingMode::Shared` 并加大缓冲。

## 4. 音频架构

### 4.1 为什么不能用 Cocos 内置音频

已核实 [cc.d.ts](D:/Cocos/editors/Creator/3.8.8/resources/resources/3d/engine/bin/.declarations/cc.d.ts)：

- `_pal_audio__AudioPlayer`（L64822）**无 `playbackRate` / `detune` 接口** → 无法对采样做变调。
- `AudioSource`（L7652）仅有 `playOneShot(clip, volumeScale)`，且受 `AudioSource.maxAudioChannel` 上限约束，超出会**丢弃**音频实例。
- `AudioClip._nativeAsset` 为 `@deprecated` 私有接口，拿到 `AudioBuffer` 无稳定路径。
- 无 ADSR、无滤波器、无实时音量自动化 → 无法实现半踏板、琴盖、明亮度补偿。

结论：Cocos 音频层连"能跑"的降级方案都勉强（需离线预渲染 88 键 × N 层，体积 ×3，且仍受 channel 上限与延迟不可控困扰）。**直接自研内核。**

### 4.2 分层架构

```text
┌─────────────────────────────────────────────────┐
│ Cocos TypeScript 层                              │
│  PianoController / KeyboardView / SettingsView   │
│  EventBatcher（每帧 flush 一次）                  │
└────────────────┬────────────────────────────────┘
                 │ 自定义 JSB 绑定（C++ ↔ TS）
┌────────────────▼────────────────────────────────┐
│ C++ 实时音频内核（双端共用，单一 .so / .a）        │
│  ┌───────────────────────────────────────────┐  │
│  │ AudioDevice  (Android: Oboe / AAudio)        │ │
│  │   ↕ 实时回调（禁止锁/分配/IO/JNI）           │ │
│  │ Mixer ← VoicePool ← VoiceScheduler          │ │
│  │   ↑ SPSC 无锁事件队列                        │ │
│  │ SamplePool（常驻 PCM）+ StreamLoader（独立线程）│ │
│  │ FX: EQ / Reverb(FDN) / 力度曲线                │ │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

### 4.3 内存策略（本方案的核心）

**思路：分音区区别对待 —— 低音区不做循环，靠流式；中高音区用循环尾换取内存。**

- **低音区 A0–A2（拒绝循环）**：常驻 attack 段，其后进入**磁盘流式接续**，播放完整的自然衰减。
  这个区域衰减慢（A0 可达 15s+），恰恰是循环点最难藏的地方；但也正因为衰减慢，**从触键到需要尾部数据有 4 秒以上的预读窗口**，流式加载完全来得及。低音区是"最难循环"与"最容易流式"的交集，用流式是最优解。
- **中高音区 C3–C8**：钢琴音在此已进入近似稳态衰减，用长交叉淡化循环接续，叠加混响后循环点基本不可闻。

按音区分级（48kHz / 16bit / 立体声 = 187.5 KiB/s）：

| 音区 | 根音数 | attack 段 | 循环段 | 单条合计 |
|---|---|---|---|---|
| A0–A2 | 9 | 4.0s | **无（尾部流式）** | 常驻 4.0s，尾部按需流式 |
| C3–B4 | 8 | 2.5s | 1.5s | 4.0s |
| C5–C8 | 13 | 1.2s | 0.8s | 2.0s |

> 根音数 9 / 8 / 13（合计 30）是与音源实测核对过的，见 §2.3。

常驻力度层数 → 常驻内存占用（低音区按 4.0s 常驻计，尾部流式不占常驻）：

| 常驻层数 | 条数 | 常驻秒数 | 常驻内存 | 适用机型 |
|---|---|---|---|---|
| 6 层 | 180 | 564s | **≈ 108 MB** | 4GB RAM 及以上（默认） |
| 8 层 | 240 | 752s | **≈ 144 MB** | 6GB RAM 及以上 |
| 16 层（全量） | 480 | 1504s | **≈ 289 MB** | 8GB RAM 高端机 |

> 对比 v0.1 的"低音区也做循环"方案（低音区 4.0s attack + 2.0s 循环 = 6.0s 常驻），
> 低音区改为流式后只需常驻 4.0s attack，常驻内存因此下降。代价是多一条流式 I/O 路径。

- 中间力度层由相邻常驻层**增益 + 高频补偿插值**生成（标准采样器做法）。
- 设置项「力度层精度」对应上表三档，启动时按 `ActivityManager.MemoryClass` / `os_proc_available_memory()` 自动推荐。
- 超出常驻表的层走**磁盘 LRU**：首次触发时从文件流式读取，读毕入缓存，缓存上限可配。
- release 层（hammer 88 条 + harm 90 条，共约 21MB）与踏板噪音**全部常驻** —— 体积小、触发率高。

### 4.4 采样器内核要点

| 模块 | 要点 |
|---|---|
| `AudioDevice` | Oboe，`LowLatency` + `Exclusive`，`setBufferSizeInFrames` 取最小稳定值；API < 27 回落 OpenSL ES。**注意 Oboe 使用 `mixing` 模式（回调送出数据），而 sfizz 是 `synthesize` 模式（回调索要数据），两者需做好线程边界** —— 见 §9.3 |
| `EventQueue` | SPSC 无锁环形队列，UI/MIDI 线程写、音频线程读。**音频回调内禁止**：锁、`new`/`malloc`、文件 IO、JNI 调用 |
| `VoicePool` | 固定 64 voice 预分配（无运行时分配）。偷取策略：优先释放态且最弱的音 > 最老的音 |
| `SamplerVoice` | 重采样用 **4 点 Hermite / Catmull-Rom 插值**（变调 ±1 半音下线性插值不够干净） |
| `SamplePool` | 预分配 PCM 内存池，常驻区 + LRU 区分离 |
| `StreamLoader` | 独立解码线程（FLAC 解码），产出写入环形缓冲；音频线程只读，无阻塞 |
| `FX` | 高架 EQ（琴盖/明亮度）+ FDN 算法混响（替代卷积，成本低且参数可控）+ 力度曲线映射 |

### 4.5 JSB 桥接

- 自定义绑定（jsb2.0 手动绑定 / sebind），暴露 `PianoEngine` 单例方法：`noteOn/noteOff/pedal/setParam/loadBank`。
- **批量提交**：TS 侧把触键事件连同时间戳先入队，在 `update()` 中每帧一次性提交给原生层。避免每事件一次跨语言调用。
- **禁用 `jsb.reflection.callStaticMethod` 传递触键事件**（JNI 反射 + 字符串解析开销会直接吃掉延迟预算）。

## 5. 音源预处理流水线

### 5.1 步骤

```text
drwx 拉取 sfzinstruments/SalamanderGrandPiano 的 Samples/*.flac
  ↓
1. 解析 Data/tune_ret.txt → 得到每个根音的音高修正值
   （选用 Retuned，整条直接使用，不做变调）
  ↓
2. 尾部裁剪：能量阈值自动判定，而非固定秒数 —— 保留自然衰减形态。
   ⚠️ 实测（§2.3）表明这一步**几乎削不掉东西**（-60dB 门限下仅 2%），
   它的定位是「去掉末尾可能的数字静音」的安全步骤，**不是体积优化手段**
  ↓
3. 循环点提取（**仅中高音区 C3–C8**）：从裁剪点前 1.5–2.0s 取循环区，
   loop_crossfade 0.5s，确保循环边界相位连续。
   低音区 A0–A2 不做循环，只导出 4.0s attack 段 + 完整尾部（供流式读取）
  ↓
4. 按音区分段导出：attack 段 + 循环段 分别成文件
  ↓
5. 编码：FLAC 48kHz/16bit（可选 24bit 档）
  ↓
6. 响度归一化：每条记录 gainCompensation，统一感知响度
  ↓
7. 生成 manifest.json + 分包（核心层 / 扩展层 / release 层）
```

### 5.2 manifest 格式（草案）

```json
{
  "version": "1.0.0",
  "sampleRate": 48000,
  "rootNotes": [
    { "note": 21, "name": "A0",
      "layers": [
        { "v": 1, "attack": "piano/A0v1_a.flac", "attackFrames": 192000,
          "loop": "piano/A0v1_l.flac", "loopStart": 0, "loopEnd": 96000,
          "crossfadeFrames": 24000, "gain": -1.2 }
      ] }
  ],
  "release": { "hammer": "rel/rel{n}.flac", "harmonics": ["harm/harmS{n}.flac"] },
  "pedal": { "up": ["pedal/pedalU1.flac", "pedal/pedalU2.flac"],
             "down": ["pedal/pedalD1.flac", "pedal/pedalD2.flac"] }
}
```

### 5.3 资源存放位置

**音频不走 Cocos 资源系统**（`AudioClip` 会带来额外拷贝、解码与内存开销）。

→ 音频文件放在**原生侧**：Android `assets/`（只读内置）或 `filesDir`（导入到可写目录）。由 C++ 层直接按路径读取，绕过 Cocos 资源系统。

Cocos 只负责 UI 与逻辑，通过 `PianoEngine.loadBank(path)` 告知原生层音频包根目录。

### 5.4 分发形态：全量随包（已定）

音源随安装包分发，**完全离线可用，无下载器**。两种发布渠道的处理方式不同：

| 渠道 | 做法 | 约束 |
|---|---|---|
| **Google Play** | 用 **AAB** 格式，音源放 **Play Asset Delivery 的 install-time asset pack** | base 模块限 200MB；单 asset pack 上限 1.5GB，265MB 可容纳。install-time 类型随安装一并下发 |
| **侧载（直接发 APK）** | 音源打进 assets | 无平台限制，但 APK 体积约 350MB+ |

**对 C++ 层的要求**：无论走哪个渠道，音源都要能被**按文件路径直接读取**（不解压、不经 Cocos 资源系统）。Play Asset Delivery 的文件安装后位于 asset pack 目录，需通过 Play Core Library 的 `AssetPackManager.getPackLocation()` 取到路径后传给原生层，或确认 install-time pack 是否可直接经 `AssetManager` 访问。

⚠️ **M6-1 需先验证的工程点**：Cocos Creator 3.8 的 Android 构建产物能否直接接入 asset pack 模块，还是必须手改 Gradle。建议开工前花 30 分钟做可行性确认 —— 它可能改变 M6 的拆分方式。

## 6. 音色与控制参数

| 参数 | 实现方式 | 说明 |
|---|---|---|
| 力度曲线 | `velocity → {层选择, 层内增益, 高频补偿}` | 5 预设 + 自定义控制点 |
| 力度层精度 | 常驻 6 / 8 / 16 层切换 | 见 §4.3，切换需重新加载 PCM |
| 混响 | FDN 算法混响，参数：size / decay / damping / mix | 3 预设（录音室 / 音乐厅 / 教堂） |
| 琴盖开合 | 高架 EQ 模拟 | ⚠️ **Salamander 为单一麦位录音，无真实多麦位**，只能靠频响模拟，非真采样 |
| 明亮度 | High-shelf + 力度联动动态 EQ | 补偿力度层插值造成的亮度损失 |
| 调律 | Retuned / Natural 两套 tune 参数 | 默认 Retuned |
| A4 基准 | 415–450Hz | 全局变调 |

**需要说明的边界**：琴盖、明亮度属于「模拟」而非真采样，Salamander 素材本身不支持多麦位与 una corda。方案文档应避免对这部分过度承诺。

## 7. 键盘 UI 与交互（横屏）

### 7.1 尺寸问题与解法

iPhone 15 Pro 横屏 852pt，88 键 → 每白键仅 16.4pt，无法准确触击（经验下限 22–24pt）。

- **默认**：显示约 2.5 个八度（白键 ~40pt），支持**双指缩放 + 横向拖动**。
- **设置项**：键宽（22–48pt 可调）、「整 88 键」模式、八度快捷切换。
- **Android 大屏平板（12"+ 横屏，约 1280–1600pt 宽）**：可一屏显示 88 键（白键 24–30pt），体验最佳 → **作为主要演示与验收设备**。手机端以缩放 + 拖动为主。

### 7.2 力度检测

- **主**：触点纵向位置（越靠近琴键外端力度越大，模拟真实杠杆）。
- **辅**：触点向下滑动速度。
- **不采用**：压感。Android 机型普遍无压感硬件，不同厂商的 `MotionEvent.getPressure()` 语义也不一致，不可依赖。
- 提供「固定力度」选项给不接受力度波动的用户。

### 7.3 其他交互

| 项 | 要点 |
|---|---|
| 多点触控 | Cocos touch 事件支持多点；需自行做命中测试，**黑键优先且命中区需扩大**（约 1.4×） |
| 滑奏 glissando | 连续触发需**去抖 + 最小触发间隔**，否则糊成一片 |
| 踏板按钮 | 屏幕左下/右下大按钮。屏幕按钮仅支持开关；接 MIDI 键盘时支持 CC64 连续值 |
| 踏板逻辑 | 踩下：挂起 release；松开：按正常 release 衰减；半踏板：release 时间按 0–127 插值 |
| 渲染 | 88 键不要每键一个 Sprite+Label 节点；用 `Graphics` 或自定义 Assembler 批量绘制 |

## 8. MIDI 输入（仅 Android）

| 通道 | 方案 |
|---|---|
| USB MIDI | `android.media.midi`（API 23+）：`MidiManager` 枚举设备 + `MidiInputPort`。需处理 USB 设备权限请求 |
| BLE MIDI | **系统无内置，需自实现 GATT MIDI 服务解析**（服务 UUID `03B80E5A-…C700`，特征 `7772E5DB-…6BF3`），含时间戳解析与丢包补偿 |

**统一要求**：原生层把 MIDI 消息转换为与触屏**完全相同**的 `PianoEvent`，走同一条 `EventQueue`。

⚠️ 时间戳对齐是本模块的主要难点：**BLE MIDI 的时间戳是 13 位毫秒、会周期性回绕**，USB MIDI 的基准又不同。两者都需要做回绕展开与基准对齐后才能映射到音频时间轴。这部分工作量不要低估。

### 9.3 音频内核：sfizz（首选路线）

**背景**：团队无原生音频开发经验。自研一个实时安全的采样器内核（voice 管理、重采样、循环衔接、流式）是中等偏上的原生音频工程，对无经验团队风险很高。因此**首选复用成熟内核**。

[sfizz](https://github.com/sfizz/sfizz) 是开源 C++ SFZ 播放器（BSD-2-Clause，商用友好），支持 ARM NEON，且 **Salamander 原仓库本身就是 SFZ 格式** —— 理论上可以直接喂给它。

若走通，M1 从 10 人日降到 2 人日，且规避了"无经验团队写实时音频内核"这个最大风险。

**M0-7 必须验证的四点：**

1. **线程模型对接**。Oboe 是 `mixing` 模式（回调**送出**数据），sfizz 是 `synthesize` 模式（回调**索要**数据）。需把 `sfizz_render_block` 调用搬进 Oboe 回调，并确保 sfizz 内部无锁、无分配地工作在这个线程上。这是集成的主要工程点。
2. **ARIA 扩展覆盖率**。Salamander 的 SFZ 用了 `#define` 宏、变量替换、`offset_oncc98`、`amplitude_oncc` 等 ARIA 专有 opcode。需实测 sfizz 能吃下多少；不支持的 opcode 可在预处理阶段（§5）降级为普通 SFZ。
3. **流式加载能力**。sfizz 默认倾向全量载入内存，与 §4.3 的常驻策略冲突。**尤其关键的是低音区尾部流式** —— 若 sfizz 不支持按需流式，低音区就只能退回"完整衰减全常驻"（8 层时约 +70MB）或"接受循环"。这一点的验证结论会反向影响 §4.3 的方案。
4. **授权与体积**。确认当前版本许可证；确认编译后 so 体积可接受。

**验证失败的降级路径**：不要直接跳到"自研内核"。无经验团队自研实时音频内核的失败概率不低，应先评估**转 H5/WebView + Web Audio** 路线（用 Cocos Web 构建，音频走浏览器 AudioContext，零原生音频代码）。该路线延迟略高但工程风险低得多。自研内核应作为最后手段。

## 11. 决策记录与待决问题

### 11.1 已决（v0.2 评审）

| # | 决策项 | 结论 | 影响 |
|---|---|---|---|
| 1 | 目标平台 | **Android 单机**，不做 iOS | 移除 iOS 设备层、CoreMIDI、IPA 构建；解除 macOS 环境依赖；工期 -0.5 周 |
| 2 | 音频内核 | **优先 sfizz**，自研降为最后手段 | M1 从 10 人日降到 2 人日；集成风险前移到 M0-7 |
| 3 | 低音区循环 | **绝对无循环**（宁可包体大），改为常驻 attack + 尾部流式 | 实质代价是**磁盘/包体**而非内存：包体 **≈430 MB**（若改长循环可压到 ≈190 MB）。见 §11.2 说明 |
| 4 | 分发形态 | **A 全量随包**，完全离线可用 | 取消下载器；Play 渠道需 AAB + install-time asset pack；侧载则 APK ≈350MB |

### 11.2 待决

1. 存储位深：16bit 还是 24bit。听感差异极小。
2. 混响用 FDN 算法 vs 卷积（卷积需额外 IR 素材与授权）。
3. 是否需要「延迟校准向导」作为正式功能（而非仅测试工具）。
4. sfizz 的**低音区流式能力**是否满足 —— 若不满足，低音区方案需回退（见 §9.3 第 3 点）。
5. 目标机型下限 —— 决定默认常驻档位是 6 层还是 8 层。

### 11.3 可选优化（供参考，暂不纳入）

如果 M0 的流式路径验证顺利，可以考虑**把中音区 C3–B4 也改为"常驻 attack + 尾部流式"**，彻底取消循环：

- 常驻内存：8 层从 154MB 降至 **≈ 136MB**
- 磁盘：从 ≈265MB 增至 **≈285MB**
- 收益：全频段无循环点，保真度更高；代价是流式通道并发数上升

这条属于"低风险后置优化"，等 M1-6 流式实现稳定后再评估，不阻塞主线。
