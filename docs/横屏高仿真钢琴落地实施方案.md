## 3. 接口契约

**本节是 M0 结束时要冻结的部分。** 冻结后 TS 侧与 C++ 侧可并行开发。

### 3.1 演奏事件结构（核心数据结构）

16 字节定长，小端。以 `ArrayBuffer` 批量传入 C++，**零拷贝**（JSB 绑定直接读 TypedArray 数据指针）。

```c
// native/engine/common/Classes/piano/Event.h
struct alignas(16) PianoEvent {
    uint8_t  type;      // 见 EventType
    uint8_t  note;      // MIDI 0..127（PedalValue 时为踏板值 0..127）
    uint8_t  velocity;  // 0..127
    uint8_t  source;    // EventSource
    float    timeMs;    // 相对音频流启动的毫秒时间戳
    uint32_t reserved0;
    uint32_t reserved1;
};
static_assert(sizeof(PianoEvent) == 16, "");
```

```ts
// assets/scripts/audio/PianoTypes.ts
export const enum EventType {
    NoteOn = 1, NoteOff = 2,
    PedalDown = 3, PedalUp = 4, PedalValue = 5,
    AllNotesOff = 6, PitchBend = 7,
}
export const enum EventSource { Touch = 0, Midi = 1, AutoPlay = 2 }
export const EVENT_STRIDE = 16;   // 字节
```

`timeMs` 语义：**事件应当发声的音频时间轴时刻**。C++ 侧 `Mixer::render` 在推进到该时刻时触发，而非"收到即触发"。这是手感的关键（见技术方案 §3.2）。

时钟基准：`AudioDevice::streamTimeMs()` 返回自 `start()` 起的音频时钟毫秒数。TS 侧首次调用 `start()` 后记录 `performance.now()` 基准，此后 `timeMs = 当前音频时钟 + 一个前瞻量`。

### 3.2 TS ↔ C++ 绑定接口

```ts
// assets/scripts/audio/PianoEngine.ts —— 对 JSB 原生对象的 TS 封装
interface IJsbPiano {
    // 生命周期
    create(sampleRate: number, framesPerCallback: number): boolean;
    destroy(): void;
    start(): boolean;
    stop(): void;

    // 音源包
    loadBank(rootPath: string): void;
    getBankProgress(): number;            // 0..1，-1 表示失败
    setPreloadLevel(level: number): void;  // 6 | 8 | 16
    getResidentBytes(): number;

    // 演奏事件（性能关键路径）
    submitEvents(buffer: ArrayBuffer, count: number): void;

    // 参数
    setParam(id: number, value: number): void;
    setForceCurve(pts: Float32Array): void;  // 长度 64，velocity/127 → gain

    // 诊断
    getActiveVoices(): number;
    getCpuLoad(): number;      // 0..1，音频回调耗时占回调周期比例
    getXrunCount(): number;
    getStreamTimeMs(): number;
}
declare const jsbPiano: IJsbPiano | undefined;   // 原生平台才有
```

**性能红线**：`submitEvents` 是全工程唯一的每帧跨语言调用。**禁止**在事件路径上使用 `jsb.reflection.callStaticMethod`、禁止为每个音符单独调用原生方法、禁止传 JSON 字符串。

### 3.4 音频回调的硬性约束

`RenderFn` 内部（即音频线程）**绝对禁止**：

- 加锁（`std::mutex`、`dispatch_sync`、`@synchronized`）
- 堆分配（`new` / `malloc` / `std::vector::push_back` / 任何可能扩容的容器）
- 文件 IO、网络、日志输出
- JNI 调用（除线程初始化时一次性 `AttachCurrentThread`）
- 抛异常、`std::function` 间接调用（可接受但需确认无分配）

代码评审时把这条作为**唯一的一票否决项**。

### 3.5 音源包目录与 manifest

```text
<packRoot>/
├── manifest.json
├── piano/     <Note>v<Layer>_a.flac   (attack 段)
│              <Note>v<Layer>_l.flac   (循环段，已烘焙交叉淡化)
├── rel/       rel<1..88>.flac
├── harm/      harmS<Note>.flac
└── pedal/     pedalU1.flac pedalU2.flac pedalD1.flac pedalD2.flac
```

> ⚠️ **实际格式已按「全无循环」方案调整**（见技术方案 §2.3）：每个主音色只有
> `attack`（常驻）与 `tail`（流式）两段，**没有循环段**。字段清单如下。
>
> 另有一项实现层面的变更：**同时产出 JSON 与二进制两份 manifest**。
> 引擎读二进制版（`manifest.bin`，30.9 KB），JSON 版保留为人类可读的契约与调试入口。
> 理由是 C++ 侧需要一个 JSON 解析器才能读 JSON，而那是几百行必须写对、必须测的代码，
> 可用的单头库又在 GitHub 上取不到；固定布局的二进制读取只要几十行且能逐字节验证。
> 两份由同一份数据生成，不会分叉。

```json
{
  "version": "1.0.0",
  "sampleRate": 48000, "bitsPerSample": 16, "channels": 2,
  "tuning": "retuned", "loops": false,
  "lowestMidi": 21, "highestMidi": 108,

  "velocityLayers": [ { "index": 1, "minVelocity": 1, "maxVelocity": 26 } ],

  "rootNotes": [
    { "midi": 21, "name": "A0",
      "layers": [
        { "velocityLayer": 1,
          "attack": "piano/A0v1_a.flac", "attackFrames": 192000,
          "tail":   "piano/A0v1_t.flac", "tailFrames":  820800,
          "gainDb": 0.0 }
      ] }
  ],

  "release": {
    "hammer":    [ { "midi": 21, "file": "rel/rel1.flac", "frames": 21600 } ],
    "harmonics": [ { "midi": 21, "variant": "L", "file": "harm/harmLA0.flac", "frames": 132000 } ]
  },
  "pedal": {
    "up":   [ { "file": "pedal/pedalU1.flac", "frames": 26400 } ],

```

**`velocityLayers` 不可省。** Salamander 的 16 个力度层是**非均匀**划分的
（最轻一层独占 1–26，最响的独占 121–127）。按等分实现会让弱奏与强奏的层次整体错位。

### M0-3 实施记录：改用 AAudio，minSdk 抬到 26

**变更**：原计划的 Oboe 换成 **AAudio 直连**。

**原因**：Oboe 需要从 GitHub 拉取，而当前网络下 `github.com` 不通。AAudio 是 NDK 平台 API，
`aaudio/AAudio.h` 与 `libaaudio.so` 都在 sysroot 里，**零外部依赖**。

**代价**：`libaaudio.so` 在 sysroot 中只从 API 26 起提供，因此：
- `native/engine/android/app/build.gradle` 里 `minSdkVersion` 写死 **26**（不再读 `PROP_MIN_SDK_VERSION`）
- 实测 `ANDROID_PLATFORM` 由 `android-21` 变为 `android-26`

抬到 26 是合理的：AAudio 的低延迟路径（独占模式、低延迟性能模式）本身就只从 26 起存在。
为 API 21–25 写 OpenSL ES 回退，等于在那些设备上主动提供更差的音频体验，
而低延迟正是本应用的核心价值。API 26 = Android 8.0（2017 年）。

⚠️ **注意**：改 `minSdkVersion` 会让 CMake 的构建目录换一个哈希
（`build/.../cxx/Debug/<hash>/`），旧的整棵编译树（实测约 2.9 GB）会变成死数据，需手工清理。

**待办**：`Game.cpp` 里有一段**临时的自启动钩子**（`PIANO_M0_AUTOSTART`），
启动即拉起音频流并播测试音，用于验证「真机出声」。M0-4 接通 JSB 后**必须删除**。

### M1 音频内核（自研路线，10 人日）

> **⚠️ 路线已由 sfizz 切换为自研。**
>
> 原计划以 sfizz 为主线，理由是团队无原生音频经验。但 M0-2 验证发现：
> sfizz 的 `external/` 是 10 个 git submodule，codeload 的 tarball 不含内容，

```text
M0-1 ─┬─ M0-2 ★ ─┬─ M1-2 ─┐

M2-1 ─ M2-2 ─ M2-3 ─ M2-4 ─────────────── M2-5 ─┐
                                                 │
M3-1 ─ M3-2 ─ M3-3 ─┬─ M3-4                      │
                    ├─ M3-5           M4-1~5 ─ M6-4
                    └─ M3-6                      │
                                                 │
M5-1 ─ M5-2 ─ M5-3 ─ M5-4     M6-1 ─ M6-2 ─ M6-5 ─ M7-x
```

**最长的依赖链**：`M2-1 → M2-2 → M2-3 → M2-4 → M2-5`（9.5 人日），其中 **M2-2（裁剪 + 循环 + 流式分段）是单项最长任务（3.5 人日）**，且质量直接决定听感上限。**建议 M0-1 完成后立即启动 M2**，不要等内核。

**可并行分支**（单人时穿插做，双人时并行）：

- `M2-1 ~ M2-4`（音源流水线）只依赖音频素材，**不依赖任何内核任务** → M0-1 结束即可动手。
- `M3-1 ~ M3-6`（键盘 UI）只依赖 TS 层接口 → **接口契约冻结（M0-4）后即可动手**。
- `M5-1 ~ M5-2`（MIDI 接入）只依赖事件队列 → M0-4 后可动手。

**M0 内部顺序**：`M0-1 → M0-2`（sfizz 验证）**最先做**，因为它决定 M1 是 2 人日还是 10 人日，甚至决定项目走原生还是 H5。
