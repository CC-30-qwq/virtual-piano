# 琴键点击区域失效定位与修复方案

- 日期：2026-09-29
- 现象：琴键大部分区域按下去没反应（点击区域不对）
- 结论：**上一次场景改动（KeyboardArea 上抬 160pt）让键盘矩形与手势区矩形重叠，手势区把触摸全部吃掉**
- 状态：**方案 A 已应用到 `Main.scene`**（§4.1），几何已核对；真机复验待做
- 上游：[移动端键盘底部被裁问题定位与修复方案](移动端键盘底部被裁问题定位与修复方案.md)（同一根因的另一个症状）

---

## 1. 结论

`Main.scene` 里 KeyboardArea 被整体上抬了 160pt（提交 `6751ee0`）：

| 字段 | 改动前 | 改动后 |
|---|---|---|
| KeyboardArea `_lpos.y` | -360 | **-200** |
| KeyboardArea Widget `_bottom` | 0 | **160** |

抬高之后，键盘矩形与**手势区（GestureArea）矩形重叠了 160pt**（键高总共 180pt）。
GestureArea 是 Canvas 下的**后一个兄弟节点**，Cocos 的触摸派发是**命中即独占** ——
它先命中、先派发、然后 `break`，键盘的 `TouchRouter` 一个事件都收不到。

**症状（三种宽高比下都一样）**：

- **黑键完全按不响** —— 黑键占键盘局部 y ∈ [68.4, 180]，整条都在重叠带里；
- **白键只有最底下约 20pt 能响** —— 局部 y ∈ [0, 20) 才是没被覆盖的那一条；
- 在这一带里按下去再往下滑也不会出声：触摸被谁认领是在 `TOUCH_START` 那一刻定的，之后不会转交。

---

## 2. 定量推算

Canvas 上没有 Widget，所以运行时 Canvas 矩形**恒为 1280×720**、世界原点在 (640, 360)；
可见区域以该原点为中心（见[上一份文档](移动端键盘底部被裁问题定位与修复方案.md) §3.1）。

| 节点 | Widget | 世界 y 范围 |
|---|---|---|
| GestureArea | flags 45（四边），bottom = 180 | **[180, 720]** |
| KeyboardArea | flags 44（左/右/底），bottom = 160 | **[160, 340]** |

按屏宽比逐档核对（`可见高 = 1280 / 宽高比`）：

| 屏幕 | 可见 y | 键盘 y | 重叠 | 占键高 | 键盘底距屏幕底 |
|---|---|---|---|---|---|
| 16:9 | [0, 720] | [160, 340] | **160pt** | 89% | **160pt** |
| 19.5:9 | [65, 655] | [160, 340] | **160pt** | 89% | 95pt |
| 20:9 | [72, 648] | [160, 340] | **160pt** | 89% | 88pt |
| 2.4 | [93, 627] | [160, 340] | **160pt** | 89% | 67pt |

**重叠量与宽高比无关，恒为 160pt** —— 也就是说这个 bug **在编辑器（16:9）里就能复现**，不必真机。
同时 16:9 下键盘底边离屏幕底边空的 160pt 也说明：这次上抬不是精确适配，是给键盘硬挪了个位置。

## 3. 证据链

### 3.1 触摸派发是「命中即独占」，不是广播

`cocos/2d/event/pointer-event-dispatcher.ts:125-141`：

```ts
for (let i = 0; i < length; ++i) {
    const pointerEventProcessor = pointerEventProcessorList[i];
    ...
    if (pointerEventProcessor._handleEventTouch(eventTouch)) {
        ...
        dispatchToNextEventDispatcher = false;
        if (!eventTouch.preventSwallow) {
            break;                    // ← 认领后直接跳出，后面的节点收不到
        }
    }
}
```

`NodeEventProcessor._handleTouchStart`（同目录 `cocos/scene-graph/node-event-processor.ts:638-651`）
用 `uiTransformComp.hitTest(pos, windowId)` 判定是否认领。

### 3.2 谁是「第一个」由兄弟顺序决定

`pointer-event-dispatcher.ts:227-259` 的 `_sortByPriority`：先按相机优先级，
再爬到公共父节点比较 `siblingIndex`，`return priority2 - priority1` → **索引大的排在前面**。

Canvas 的子节点顺序是 Background(0)、KeyboardArea(1)、**GestureArea(2)**，
所以 GestureArea 永远先于键盘被判定。

### 3.3 命中测试用的是矩形，不是「看得见的像素」

`cocos/2d/framework/ui-transform.ts:460-` 的 `hitTest`：把屏幕点换算到节点局部空间，
再判 `0 ≤ x ≤ width && 0 ≤ y ≤ height`。

GestureArea 有 UITransform 1280×540（`Main.scene` 对象 18），
所以它**虽然什么都不画，却实打实地占着 [180, 720] 这块触摸区域**。
「看不见的节点也能吃触摸」是这件事最反直觉的地方。

### 3.4 键盘本身的命中逻辑是对的

`KeyboardInput.touchStart` → `KeyLayout.hitTest`（黑键优先、命中区外扩 1.4 倍）
与坐标换算（`camera.screenToWorld` + `convertToNodeSpaceAR`）都自查过，
在这次改动之前没有改动、也没有问题。**问题不在命中算法，在事件压根没送到。**

## 4. 根本问题

两套触摸区域（琴键 / 手势区）必须**严格铺满且不相交**，但它们的尺寸由**两份互不知道的
Widget 配置**各自决定，其中一个还依赖「Canvas 矩形 == 可见区域」这个当前不成立的前提：

```
键盘底边 = Canvas底 + KeyboardArea.bottom
手势区底边 = Canvas底 + GestureArea.bottom(180)
```

只要 `KeyboardArea.bottom ≠ 0`，两者必然错位：调小了 → 键盘被裁（原问题）；
调大了 → 重叠、按键失效（本问题）。**能选的只有 0 这一个值。**

---

## 5. 修复方案

### 5.1 方案 A（推荐）：补上 Canvas 的 Widget，并把 bottom 改回 0 — ✅ 已应用

即[上一份文档](移动端键盘底部被裁问题定位与修复方案.md) §4.1 的方案 A：

1. 给 Canvas 节点加 `cc.Widget`（四边对齐、偏移全 0，`_alignMode: 1`）；
2. KeyboardArea 的 `_bottom` 改回 **0**（`_lpos.y` 无所谓，Widget 会覆盖）。

生效后：

- Canvas 矩形被拉伸成**真实可见区域** → 键盘底边正好落在屏幕底边，不再被裁，也不用再硬挪；
- GestureArea 的 bottom=180 就是键盘顶边 → **两者严丝合缝，无重叠、无缝隙**；
- 两个症状（底部被裁 + 点击区域失效）**一并消失**，且以后调键盘高度不会再互相打脸。

| 项 | 影响 |
|---|---|
| TS 代码 | 0 行 |
| 键盘键宽 | 不变（fitWidth 下可见宽恒为 1280） |
| 触摸映射 | 不变 |
| 风险 | 依赖引擎「Canvas 挂 Widget 会拉伸到可见区域」的隐式约定，**需真机复验一次** |

### 5.2 方案 B（应急）：让手势区避开键盘

不动 Canvas，把 GestureArea 的 `_bottom` 从 180 改成 **340**（= 键盘顶边）。
能立刻让琴键恢复，但：

- 340 是跟着「键盘被上抬 160」凑出来的魔数，键盘高度或抬升量一变就又错位；
- 键盘底部仍会悬空（16:9 下空 160pt、20:9 下空 88pt），下面留一条死区。

**只适合当作临时验证手段，不适合作为最终状态。**

### 5.3 方案 C（防御）：加一条重叠自检

无论选哪个方案，建议补一个启动期自检：读 KeyboardArea 与 GestureArea 的世界矩形，
若有交叠就在控制台打一条明确的警告（含两块矩形的实际数值）。

理由：这类错位的症状（「按键没反应」）与「音频没载入」「事件没送达」长得一模一样，
而真实原因是布局 —— 没有这条自检，每次都要从头查一遍。
成本约 0.2 人日，纯新增、不改现有行为。

## 6. 已做与待验

### 6.1 已应用到 `Main.scene` 的改动（共 3 处）

| # | 位置 | 改动 |
|---|---|---|
| 1 | Canvas 节点（`__id__: 2`）的 `_components` | 追加 `{"__id__": 32}` |
| 2 | 场景对象 `__id__: 32`（新增） | `cc.Widget`：`_alignFlags: 45`（四边）、偏移全 0、`_alignMode: 1`（ALWAYS）、`node` 指向 Canvas |
| 3 | KeyboardArea 的 Widget（`__id__: 16`） | `_bottom` 160 → **0** |

`_alignMode` 取 1（ALWAYS）是为了与场景里既有的 Background / GestureArea 一致 ——
它们都是 1，单独给 Canvas 用别的模式反而会多出一个「谁在什么时候对齐」的时序差异。

**注意 `_alignMode: 1` 与引擎里那几个锁标志的关系**：`Canvas.__preload()` 在
`widget.updateAlignment()` **之后**才给 Canvas 打 `IsPositionLocked / IsSizeLocked /
IsAnchorLocked`，而且只在编辑器里打（`EDITOR_NOT_IN_PREVIEW` 分支）。
这几个标志运行时只是给编辑器检查器看的（见 `cocos/core/data/object.ts:58-68`），
**不参与、也不会阻断 Widget 的尺寸调整** —— 所以运行时能被拉伸，编辑器里仍显示 1280×720。

### 6.2 修复后的几何（已核对）

| 屏幕 | 可见高 | 键盘 y | 手势区 y | 重叠 | 键盘底距屏幕底 |
|---|---|---|---|---|---|
| 16:9 | 720 | [0, 180] | [180, 720] | **0** | 0 |
| 19.5:9 | 591 | [0, 180] | [180, 591] | **0** | 0 |
| 20:9 | 576 | [0, 180] | [180, 576] | **0** | 0 |
| 2.4 | 533 | [0, 180] | [180, 533] | **0** | 0 |

两者严丝合缝：既无重叠（琴键不会被吃掉），也无缝隙（不留死区）。
顺带把左上角调试读数也拉回了可见区域（原先在 20:9 上位于世界 y=704，在屏幕之外）。

### 6.3 仍未做

1. **真机复验**（§7 的验收表）—— 场景改动本身只能靠真机/预览确认。
   特别要试：**黑键是否恢复响应**（它是这次回归里受害最彻底的：整条都在重叠带里）。
2. **§5.3 的重叠自检** —— 建议加。这类错位的症状（「按键没反应」）与
   「音频没载入」「事件没送达」长得一模一样，没有自检每次都要从头查一遍。约 0.2 人日。
