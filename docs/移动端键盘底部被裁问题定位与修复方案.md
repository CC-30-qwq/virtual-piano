# 移动端「钢琴底部显示不全」问题定位与修复方案

- 日期：2026-09-29
- 现象：移动端（横屏）钢琴键盘底部被裁掉，看不全
- 范围：`Main.scene` 的 UI 布局 + Cocos 分辨率适配。**不涉及**音频、键盘几何、触摸路由、手势
- 上游：[横屏高仿真钢琴技术方案](横屏高仿真钢琴技术方案.md)、[项目代码功能清单与解耦方案](项目代码功能清单与解耦方案.md)
- 方法：读 Cocos Creator **3.8.8 引擎源码**（`D:/Cocos/editors/Creator/3.8.8/resources/resources/3d/engine`）+ 按设计分辨率与可见区域做定量推算
- ⚠️ 状态：**定位结论来自源码推演，尚未真机复验**。§6 第 1 项是能在 30 秒内证伪本结论的判别问题

## 1. 结论

**Canvas 节点的矩形（1280×720）不等于屏幕的实际可见区域。**

设计分辨率是 1280×720 且 **fitWidth**（`settings/v2/packages/project.json`）。fitWidth 的含义是「按宽度缩放，高度不够就裁」：
任何宽高比**比 16:9 更宽**的屏幕，可见高度都小于 720，而 Canvas 节点仍然按 1280×720 参与布局。

挂 `cc.Widget` 的节点，其对齐基准是**父节点的矩形**（见 §3.1 证据）。于是：

| 节点 | Widget 对齐方式 | 结果 |
|---|---|---|
| Background | TOP+BOT+LEFT+RIGHT | 铺满 Canvas 矩形 1280×720。比可见区域**大**，看不出问题 |
| KeyboardArea | LEFT+RIGHT+BOT | 底边贴在 Canvas 矩形的 y=0，而 y=0 **在屏幕底边之下** → 底部被裁 |
| GestureArea | TOP+BOT+LEFT+RIGHT，bottom=180 | 同样整体上移，只是它本来就在上半部分，看不出问题 |

**只有贴底的键盘会暴露这个错位**，所以症状表现为「钢琴底部显示不全」。

## 2. 定量推算（不同宽高比下的裁剪量）

可见高度（设计单位）= `1280 / 宽高比`；上下各裁掉 `(720 - 可见高) / 2`。
键盘白键高 180，故被裁掉的比例 = `裁掉量 / 180`：

| 屏幕 | 宽高比 | 可见高 | 上下各裁 | **键盘被裁比例** |
|---|---|---|---|---|
| 16:9（1920×1080） | 1.778 | 720 | 0 | **0%（今天在桌面/编辑器看到的样子）** |
| 18:9（2160×1080） | 2.000 | 640 | 40 | 22% |
| 19.5:9（2340×1080） | 2.167 | 591 | 65 | 36% |
| 20:9（2400×1080） | 2.222 | 576 | 72 | **40%** |
| 21:9（2520×1080） | 2.333 | 549 | 86 | 48% |
| 2.4（构建配置上限） | 2.400 | 533 | 93 | 52% |

也就是说：**在主流全面屏手机上，键盘高度有一半左右在屏幕外**。
这个量级与「底部显示不全」的描述一致，也解释了为什么在桌面浏览器/编辑器里完全正常 —— 那里是 16:9，裁剪量为 0。

> 注：Android 构建配置里 `maxAspectRatio: 2.4`（`profiles/v2/packages/android.json`）只影响超宽屏的适配，不影响本问题。

## 3. 证据链

### 3.1 Canvas 的矩形在运行时**不会**跟着屏幕变

`cocos/2d/framework/canvas.ts:173`：

```ts
public __preload (): void {
    // Stretch to matched size during the scene initialization
    const widget = this.getComponent('cc.Widget') as unknown as Widget;
    if (widget) {
        widget.updateAlignment();          // ← 只有 Canvas 上挂了 Widget 才会「拉伸到匹配尺寸」
    } else if (EDITOR_NOT_IN_PREVIEW) {
        this.fitDesignResolution_EDITOR!(); // ← 编辑器里按设计分辨率对齐
    }
    ...
```

- 运行时（`EDITOR_NOT_IN_PREVIEW` 为假，即真机与浏览器构建）：**没有 Widget 就什么都不做**，Canvas 保持场景里序列化的 1280×720。
- `_onResizeCamera()`（同文件 `:223`）只调整相机的 `orthoHeight` 与位置：

```ts
const size = screen.windowSize;
this._cameraComponent.orthoHeight = size.height / view.getScaleY() / 2;   // == 可见高 / 2
this.node.getWorldPosition(_worldPos);
this._cameraComponent.node.setWorldPosition(_worldPos.x, _worldPos.y, 1000); // 相机跟到 Canvas 原点
```

相机是 Canvas 的子节点，因此**可见区域永远以 Canvas 节点的原点为中心**。
可见高 = 2×orthoHeight = 576（20:9 时），而 Canvas 矩形高 720 → 上下各多出 72，这 72 全在屏幕外。

### 3.2 Widget 的对齐基准是父节点矩形，不是屏幕

`cocos/ui/widget.ts:40`：

```ts
export function getReadonlyNodeSize (parent: Node | Scene) {
    ...
    if (parent instanceof Scene) {
        if (EDITOR) { return View.instance.getDesignResolutionSize(); }  // 编辑器：1280×720
        return visibleRect;                                              // 运行时：实际可见区域
    } else if (parentUITransform) {
        return parentUITransform.contentSize;                            // 普通节点：父节点矩形
    }
```

`cocos/ui/widget-manager.ts:64`：

```ts
const useGlobal = target instanceof Scene || !target.getComponent(UITransform);
```

`widget-manager.ts:142`：

```ts
if (isRoot) { localBottom = visibleRect.bottom.y; localTop = visibleRect.top.y; }  // 对齐屏幕
else        { localBottom = -targetAnchor.y * targetHeight; ... }                  // 对齐父节点矩形
```

**关键推论：只有父节点没有 UITransform（或父节点就是 Scene）时，Widget 才对齐真实屏幕。**
KeyboardArea 的父节点是 Canvas，而 Canvas 有 UITransform（1280×720）→ 走 `else` 分支，对齐的是 Canvas 矩形。
这正是本问题的机制，也是引擎预留的解法：**给 Canvas 本身挂 Widget**，它的父节点是 Scene → 走 `visibleRect` 分支 → Canvas 矩形被拉伸成可见区域。

### 3.3 场景里的实际数值

[Main.scene](../assets/scenes/Main.scene)：

| 节点 | 字段 | 值 | 位置 |
|---|---|---|---|
| Canvas | `_lpos` | (640, 360) = 设计分辨率的一半 | Main.scene:91 |
| Canvas | UITransform `_contentSize` | 1280 × 720 | Main.scene:703 |
| Canvas | `_components` | 只有 UITransform、Canvas —— **没有 Widget** | Main.scene:82 |
| KeyboardArea | Widget `_alignFlags` | 44 = LEFT\|RIGHT\|BOT（不含 TOP，所以高度不被拉伸，保持 180） | Main.scene:554 |
| KeyboardArea | Widget `_bottom` | 0 | Main.scene:559 |
| KeyboardArea | UITransform `_contentSize` | 1280 × 180 | Main.scene:532 |
| Keyboard | UITransform | 2080 × 180，锚点 (0,0) | Main.scene:448 |

`KeyboardView.onLoad` 拿的是父节点（KeyboardArea）的宽度当视口宽度（[KeyboardView.ts:117-119](../assets/scripts/keyboard/KeyboardView.ts#L117-L119)）。
该处注释写着「它（KeyboardArea）在 Canvas 的 `__preload` 里已由 Widget 完成对齐」——
**作者假定 Canvas 上挂了 Widget，但场景里并没有。** 方案 A 正好补上这个缺失的前提。

### 3.4 同一根因的第二个症状：左上角调试读数在移动端也不可见

`DebugHud` 挂在 Canvas 上、贴 Canvas 左上角（[DebugHud.ts:64-68](../assets/scripts/ui/DebugHud.ts#L64-L68)）：
`left = -width/2 + 20`、`top = height/2 - 16` → Canvas 局部 (-620, 344) → 世界 (20, 704)。

20:9 设备上可见区域是世界 y ∈ [72, 648]，**704 在屏幕上方之外** → 读数整块看不见。
它是「整体上移 72」的另一个直接观测点，因此可以直接当判据用（见 §6 第 1 项）。

## 4. 修复方案

### 4.1 方案 A（推荐）：给 Canvas 节点加一个 Widget

在 `Main.scene` 的 Canvas 节点上补一个 `cc.Widget`：

```json
{
  "__type__": "cc.Widget",
  "_name": "",
  "_objFlags": 0,
  "__editorExtras__": {},
  "node": { "__id__": 2 },
  "_enabled": true,
  "__prefab": null,
  "_alignFlags": 45,
  "_target": null,
  "_left": 0, "_right": 0, "_top": 0, "_bottom": 0,
  "_horizontalCenter": 0, "_verticalCenter": 0,
  "_isAbsLeft": true, "_isAbsRight": true, "_isAbsTop": true, "_isAbsBottom": true,
  "_isAbsHorizontalCenter": true, "_isAbsVerticalCenter": true,
  "_originalWidth": 1280, "_originalHeight": 720,
  "_alignMode": 1,
  "_lockFlags": 0,
  "_id": "..."
}
```

同时把该对象加进 Canvas 的 `_components`。`_alignFlags: 45` = TOP\|BOT\|LEFT\|RIGHT，与场景里 Background / GestureArea 一致；`_alignMode: 1` 也与它们一致。

生效链路（全部是引擎既有机制，无新增代码）：

1. `Canvas.__preload()` → `widget.updateAlignment()`
2. 该 Widget 的目标是 Scene（父节点）→ `getReadonlyNodeSize` 返回 `visibleRect` → Canvas 被设成 **1280 × 可见高**、位置 **可见高 / 2**
3. `_onResizeCamera()` 随后把相机对到 Canvas 原点 → **Canvas 矩形 == 可见区域**（此时二者严格相等）
4. 之后所有子节点的 Widget 都对齐到这块正确的矩形：背景铺满、键盘 180 高贴底、手势区 = 可见高 − 180

对现有代码与编辑器的影响：

| 项 | 影响 |
|---|---|
| TS 代码 | **0 行改动** |
| 编辑器场景视图 | Canvas 仍显示 1280×720（`getReadonlyNodeSize` 在编辑器里返回设计分辨率），外观不变 |
| 场景序列化 | Canvas 的 `_contentSize`/`_lpos` 不变（引擎会把 Canvas 标记为 IsSizeLocked/IsPositionLocked） |
| 键盘键宽 | 不变。fitWidth 下可见宽**恒等于**设计宽 1280，故 `keyWidth = 1280/52 ≈ 24.6pt`、88 键一屏铺满的现状保持 |
| 触摸命中 | 不变。`TouchRouter` 走 `camera.screenToWorld` + `convertToNodeSpaceAR`，相机与 Canvas 同步移动，映射自洽 |

代价与风险：

- 依赖引擎「Canvas 挂 Widget 就会拉伸到可见区域」这条隐式约定（`canvas.ts:173` 的注释 "Stretch to matched size during the scene initialization" 即为此而写）。**需要一次真机复验**（§7）。
- 手改场景 JSON 有一定风险，建议：你在编辑器里给 Canvas 拖一个 Widget（四边对齐、偏移全 0），我再按你的版本对齐代码 —— 或者我直接改 JSON，你打开编辑器确认。

### 4.2 方案 B（备选）：加一个 `ScreenFit` 脚本

新建 `assets/scripts/ui/ScreenFit.ts` 挂在 Canvas 上：`onLoad` 读 `view.getVisibleSize()` 设 Canvas 的 UITransform 尺寸与位置，并监听 `view.on('canvas-resize')` 重算。

- 优点：显式、不依赖引擎隐式机制、纯计算部分可在宿主机跑单测（符合《功能清单与解耦方案》判据 1）
- 缺点：**重复实现引擎已有能力**，并引入第二个「谁负责画布尺寸」的事实来源（违反判据 4）。仅当方案 A 在真机上不成立时才启用

### 4.3 方案 C（不推荐）：改分辨率策略

把 `fitWidth` 改成 `fitHeight`，或策略改 `SHOW_ALL`。只能消掉竖直裁剪，但：

- `fitHeight`：可见宽会大于 1280，而 Canvas 矩形仍是 1280 → 背景铺不满，左右出现黑边
- `SHOW_ALL`：整屏留黑边，键盘还会变小

两者都只是把「底部裁掉」换成「左右有黑边」，且键盘不能再铺满屏幕宽度 —— 对钢琴不合适。

## 5. 顺带发现的两个相关问题（建议另开一次做，不混进本次修复）

### 5.1 键盘宽度不响应尺寸变化（隐患，今天不发作）

`KeyboardViewport.setViewportWidth()` 已实现，但**全工程没有任何地方调用它**（`assets/scripts/` 全量检索确认）。
`KeyboardView.onLoad` 只读一次父节点宽度，之后再不更新。

- 今天不发作：fitWidth 下可见宽恒为 1280，恰好等于场景里 KeyboardArea 的宽度
- 会发作的场景：分屏 / 折叠屏展开 / 未来改分辨率策略 → 键宽与视口不匹配
- 另外 `KeyboardView.ts:114-116` 的注释把「KeyboardArea 的对齐时机」理解成 `Canvas.__preload`，实际是 `WidgetManager.refreshScene` 在**首帧 AFTER_UPDATE** 才对齐（晚于 `onLoad`）。恰好两者宽度都是 1280 才没出问题

### 5.2 安全区（刘海）未处理

`native/engine/android/app/src/com/cocos/game/AppActivity.java` 所在的模板设置
`layoutInDisplayCutoutMode = SHORT_EDGES`：横屏时刘海在**左右短边**，最左/最右的白键可能被挖孔遮住。
底部的导航栏问题则不存在 —— `CocosActivity.setImmersiveMode()` 用了 `SYSTEM_UI_FLAG_HIDE_NAVIGATION | IMMERSIVE_STICKY` 隐藏了导航栏，所以底部不会再有系统栏覆盖。

是否需要处理取决于目标机型，见 §6 第 4 项。
