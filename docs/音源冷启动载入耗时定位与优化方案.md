# 音源冷启动载入耗时定位与优化方案

> 现象：游戏启动后要等很长一段时间才有声音，等待期间画面是死的。
>
> **硬约束（2026-09-29 追加）：不允许降低音质。**
> 因此本版**删除了原方案里的「力度层降档」项** —— 16 层全常驻成为不可动摇的前提，
> 所有优化只走「不改变任何一个采样字节」的路子。逐项取舍见 §3、§5。
>
> 本文只做**定位 + 分档优化项**。每项都标了收益、代价、改动面与风险。

### 这次顺带修掉的两个隐患

1. **跨线程发布没有内存序保证**。载入线程写完银行后经 `pool.setBank()` 交给音频线程，
   而它原本是**裸指针赋值** —— ARM 弱内存序下音频线程可能「读到了新银行、却读到半成品
   层指针」。已改为 `std::atomic<SampleBank*>` 的 release/acquire（`VoicePool.h/.cpp`），
   `_sampleRate` 同样原子化。
2. **载入线程与析构的竞态**。`destroy()` 现在先 `join()` 载入线程，
   且**排在 `created` 判断之前** —— 否则载入线程会在对象析构后继续往已释放的内存里写。

### 新增的 API 语义（TS ↔ C++）

```
jsbPiano.loadBank(mask)          → 1 已受理 / 0 未受理      （**不再表示「已载完」**）
jsbPiano.getLoadProgress()       → -2 失败 / -1 未开始 / 0..99 / 100 完成
```

TS 侧对应 `AudioBackend.beginLoadBank()` 与 `loadPercent`（取值用 `LOAD_FAILED` /
`LOAD_IDLE` / `LOAD_DONE` 三个常量，别在调用点写裸数字）。

### 验收（音质不变的硬口径）

`tests/cpp/samplebank_test.cpp` 新增三组用例，随 `bash tests/cpp/run.sh` 一起跑：

- `并行与串行的 PCM 逐字节相同` —— 6 层逐字节 `memcmp`
- `失败路径下并行与串行仍逐字节相同` —— 部分失败时的压实结果也一致
- `进度回调覆盖 1..6 各一次` —— 没有 job 被漏掉

## 1. 现状：一次冷启动的载入路径

调用链（自上而下，全部在**主线程**）：

```
PianoController.onLoad()
  ├─ _engine.create() / start()            ← AAudio 流先跑起来（此时无音源，回调空转）
  └─ scheduleOnce(0.1s) → loadBank()
        └─ PianoEngine.loadBank()          默认 layerMask = -1
              └─ jsbPiano.loadBank(-1)
                    └─ PianoBridge.jsbLoadBank(-1) → mask = 0xFFFF（全 16 层）
                          └─ PianoEngine::loadBank()
                                ├─ readFile("manifest.bin")          31 KB
                                ├─ bank.loadManifest(...)            建索引
                                ├─ bank.setLayerMask(0xFFFF)
                                └─ bank.loadResident(source)
                                      ├─ pool.reserve(66,048,000 帧) 一次性 252 MB
                                      └─ for 480 个 attack FLAC:
                                            AAssetManager_open
                                            drflac_open_and_read_pcm_frames_s16   ← 全解码
                                            memcpy 到池
                                            drflac_free + AAsset_close
                          └─ pool.setBank(&bank) / setSampleRate()
```

### 关键实测量（本地对 `build-bank/` 统计，非估算）

| 项目 | 数值 |
|---|---|
| 根音数 × 力度层 | 30 × 16 = **480 条 attack** |
| attack FLAC 总字节 | **54.4 MB**（平均 113 KB/条） |
| 解码后常驻 PCM | **252.0 MB**（66,048,000 帧 × 4 B，48 kHz/16bit/立体声） |
| 解码膨胀比 | **4.65×** |
| 每层 PCM | 15.7 MB（16 层完全均匀） |
| 本次**不读**却打进 APK 的素材 | tail 148.3 MB + harm/rel/pedal 7.6 MB = **155.9 MB** |

> 注意：`tail` / `harm` / `rel` / `pedal` 四类素材在 `manifest` 里有，但**当前代码没有任何一处读取它们**（全仓 grep 零引用）——`loadResident` 只读 attack。这是 M1-6 流式与后续任务才用的数据。

### 三个结构性问题

1. **全 16 层常驻、共 252 MB**。在「不允许降低音质」的前提下，这是**必须接受的固定成本**，不再是可调项。
2. **完全同步、单线程、无进度、无 yield**。`loadResident` 是一个 480 次迭代的串行 for 循环，中途不返回。主线程在这几秒里什么都干不了 —— 画面冻结，Android 上还有 ANR 风险。现在只是用 `scheduleOnce(0.1)` 推迟了开始时刻，**没有改变「一旦开始就冻住」**。
3. **assets 里的 FLAC 被 APK 二次压缩**。`native/engine/android/app/build.gradle` 里没有任何 `noCompress` 配置，而 AGP 默认的免压缩后缀表只有 `wav/mp3/ogg/aac/…`，**不含 `flac`**。

## 2. 五个耗时来源（按预估量级排序）

| 编号 | 来源 | 说明 | 预估占比 |
|---|---|---|---|
| **S1** | 单线程 FLAC 解码 480 条 → 252 MB PCM | dr_flac 是纯标量实现，无 SIMD；移动端大核约 20–40 MB/s 输出。252 MB ÷ 30 MB/s ≈ **8.4 s** | ~70–80% |
| **S2** | 压缩资产的读取代价 | 压缩资产没有真正的随机访问：AssetManager 内部维护 inflate 流，**回退 seek 要重新开始**。而 dr_flac 打开时会先 seek 到文件尾取总长 —— 等于每个文件可能被解压两遍；`AAsset_read` 也走 inflate 而不是直读页 | ~10% |
| **S3** | 252 MB 池 reserve + 主线程 memcpy + 首次触碰页错误 | memcpy ≈ 0.3 s，页错误随大页分配而增加 | ~10% |
| **S4** | 480 次 open/close + FLAC 头解析 | 固定开销 | ~5% |
| **S5** | 与音频回调争 CPU | `create/start` 在 `loadBank` **之前**，主线程满载解码时 AAudio 回调仍在跑，加剧卡顿与欠载 | 不增加时长，但放大卡顿观感 |

**桌面实测（2026-09-29 补）**：把工程自带的 `dr_flac.h` 拿到本机编成基准
（`tests/cpp/.bench/drflac_bench.cpp`），解真机实际载入的那 480 个 attack：

| 配置 | 墙钟 | 吞吐 |
|---|---|---|
| 单线程 | **845 ms** | 298 MB/s |
| 4 线程 | **267 ms** | 944 MB/s（3.2×） |

也就是说 **解码本身并没有想象中那么贵** —— 252 MB PCM 单线程不到 1 秒。
按「手机大核比桌面核慢 3–5×、并行有效系数 2.5–3×」外推，
真机上改造后应是 **1–3 s** 量级，而不是原先估的 8–12 s。

⚠️ **原估算（中端机 8–12 s）偏高，已作废**。当时的错误在于把 dr_flac 的吞吐
按 20–40 MB/s 估（实测桌面就有 298 MB/s）。真机耗时以 §6.1 的日志为准。

顺带排除掉一个候选杠杆：把 FLAC 重编码成 `-compression_level 0`（无损、企图换更快的解码）
实测**解码反而慢 1.22×、体积还大 1.19×**，两头都亏 —— 这条路不用再考虑。

## 3. 优化项

> **每一项都不改变音质**：不改数据、不改层数、不改采样率、不改任何已录制的内容。
> 表中「音质影响」一列全部为**无**，这是本轮选型的硬门槛。

### P0-0　加分段计时（0.5 人日）— 先做，作为决策依据

在 `PianoEngine::loadBank` 与 `SampleBank::loadResident` 里插计时，分四段打到 logcat（`PIANO_LOG_INFO` 已有）：

```
manifest / 池分配 / 解码+读取 / memcpy    以及 480 条的累计与单条均值
```

**不改任何行为**，只是让后面的取舍有数据支撑。S2 是否成立（压缩资产是否真在重复解压）也能靠「单条耗时 vs 文件大小」的相关性看出来。

| 音质影响 | 改动面 | 风险 |
|---|---|---|
| 无（只加日志） | C++，2 处 | 无 |

---

### P0-1　`noCompress 'flac'`（0.2 人日）

`native/engine/android/app/build.gradle` 增加：

```gradle
android {
    androidResources {
        noCompress += 'flac'      // AGP 8 已移除 aaptOptions，不能用旧写法
    }
}
```

- **收益**：APK 构建不再对 208 MB 已压缩数据做 deflate（构建也快）；运行时资产直读，消除 S2 的重复解压路径。
- **代价**：APK 体积可能略增（FLAC 二次压缩收益本就接近 0，甚至因 deflate 头而略增）。
- **为什么不动音质**：APK 里存的是**同一份 FLAC 字节**，只是不再套一层压缩壳。运行时解出的 PCM 逐字节相同。

| 音质影响 | 改动面 | 风险 |
|---|---|---|
| **无**（数据字节不变） | gradle 3 行 | 低；需实测 APK 体积增幅 |

---

### P0-3　后台线程载入 + 进度显示（1.5–2 人日）

把 `loadResident` 挪到工作线程，主线程每帧查询进度（新增 `jsbPiano.getLoadProgress()`），HUD 显示「音源载入 42%」。

- **收益**：**不减少总时长**，但消除主线程冻结与 ANR 风险，用户看得见进度，而不是面对死画面。**体感改善最大的一项**，且完全不动数据。
- **关键约束**（全部风险点在这里）：
  - `SamplePool::reserve/commit` 会从主线程改到工作线程执行，而音频线程要读池。现在 `pool.setBank()` 是**裸指针赋值**，跨线程没有可见性保证（ARM 弱内存序下音频线程可能读到半成品层指针）。必须改成 atomic release/acquire 或加锁做**一次性切换**。
  - 切换点天然存在：`setBank` 在 `loadResident` 全部完成之后才调用，而 `VoicePool::noteOn` 开头就判 `_bank == nullptr || !_bank->loaded()`，所以「看到新 bank」之前音频线程不会读池。
  - 载入期间 `_bank` 仍为空 → 按键无声，这是预期行为（HUD 已显示音源状态）。
- 可顺带调顺序：**先载完再 `start()`**，避免 S5 的空转争抢；代价是载入期间彻底无声（本来也是无声）。

| 音质影响 | 改动面 | 风险 |
|---|---|---|
| **无** | C++ 线程化 + JSB 新增 1 个进度查询 + TS 轮询 | 中；线程可见性必须做对 |

---

### P1-1　并行解码（1.5–2 人日）★ 本轮主要提速手段

把 480 条按根音切成 N 份，N 个工作线程各解码到池内**预先算好偏移**的区段。

- **收益**：这是「不降质」前提下最大的一次提速。4 核估 2.5–3×，6 核估 3–4×（8–12 s → 2–3 s）。
- **为什么不动音质**：每个线程仍是同一个 `dr_flac` 解同一条文件、写入同一段偏移，**产出逐字节相同**，只是并行。
- **代价**：`SamplePool` 现在是单线程 bump 分配器（`scratch()` / `commit()`），要改成「先算好每层目标偏移 → 并发直写」，分配器语义要重写；线程数要避开音频线程所在核。
- **依赖**：P0-3 的线程安全改造是本项前置。

| 音质影响 | 改动面 | 风险 |
|---|---|---|
| **无**（逐字节相同） | SamplePool 重写 + SampleBank 并行化 + 线程池 | 中高；集中在分配器语义 |

---

### P2-1　渐进式载入 —— **必须按「音区完整」切，不能按「力度层」切**（2 人日，本轮可选）

按音区优先级排序载入（先中央几个八度，再向两侧扩），每完成一个音区就把它并入查表。

- **收益**：首声延迟从 2–3 s 降到 < 1 s。
- **关键设计约束（因为不允许降低音质）**：
  - ❌ **不能**「先给每个根音载 3 个层、之后再补齐」—— 那样在补齐之前，所有音都在用**相邻层顶替**，是实打实的音质下降。
  - ✅ **要**「先把中央音区的**全部 16 层**载完，再载下一个音区」。这样任一时刻能发声的键**都是满层、逐字节准确的**，只是**能弹的音域在逐步扩大**。已发声的部分没有任何妥协。
- **代价**：载入期间键盘上「还没轮到的音区」按下去不响（HUD 可显示已就绪音域）。这是**可用性**的取舍，不是音质的取舍。
- **依赖**：P0-3 + P1-1。若 P1-1 已把总时长压到 2–3 s，本项的边际收益不大，可以不做。

| 音质影响 | 改动面 | 风险 |
|---|---|---|
| **无**（已就绪音区满层准确） | 载入排序 + 查表增量可用 + 进度分音区显示 | 中 |

---

### P2-2　顶替补偿（0.5 人日，动机已变，可选）

`SampleBank::findLayer` 在目标层缺失时会退到最近的已载入层（合理），但
`VoicePool::velocityGain` 算的是**请求力度所在区间**的层内微调（±3 dB），而不是**实际使用的那一层**。
正确做法：按**实际层的区间**算层内微调，再乘「实际层 ↔ 请求层」的层间增益偏移。

- **动机已变**：原方案里这是「降到 6 层」的前置；现在不降档，它只在**载入失败**（个别 FLAC 读不出来）时才被触发。
- **结论**：优先级下调，可作为健壮性补丁，不阻塞主线。

| 音质影响 | 改动面 | 风险 |
|---|---|---|
| 无（只让回退更接近原层） | VoicePool 1 处 | 低 |

---

### P2-3　格式预处理：未压缩 PCM + 轻量压缩（备选，需权衡体积）

把 attack 段从 FLAC 改成 **raw PCM + LZ4**（或干脆未压缩）打进音源包。
LZ4 解压约 2 GB/s，**解码耗时几乎归零**，载入退化为纯 I/O（252 MB 顺序读 ≈ 1–2 s）。

- **为什么不动音质**：PCM 是 FLAC 解码后的**同一份数据**，逐字节相同；LZ4 是无损压缩。
- **代价**：音源包攻击段从 54 MB 涨到约 210–250 MB（**APK 体积翻数倍**）。
  与方案 §6-2 的包体约束（Play base 模块 ≤ 200 MB、侧载 APK 约 350 MB）**直接冲突**，
  除非 M6-1 的 asset pack 已落地、且接受更大的下载量。
- **结论**：先记在账上。若 P1-1 的 2–3 s 仍不可接受，再回头评估。

| 音质影响 | 改动面 | 风险 |
|---|---|---|
| **无**（无损） | 流水线换编码 + `SampleSource` 换解码器 | 高（包体） |

### P2-4　155.9 MB 完全没用上的素材仍打进 APK

`tail`(148.3 MB) + `harm`/`rel`/`pedal`(7.6 MB) 当前代码零引用，但构建时照打不误。
对**载入耗时无影响**（不读），但让 APK 白胖 156 MB。

- 已决定：**不动，等 M1-6**。（记账，避免将来改两遍。）

## 5. 建议的执行顺序

```
P0-0 计时  →  P0-1 noCompress  →  P0-3 后台载入+进度  →  P1-1 并行解码
                                                              ↓
                                                    （仍嫌慢再做 P2-1 分级载入）
```

理由：先测量（P0-0）避免优化错的地方；`noCompress` 零风险先摘；后台载入（P0-3）解决体感最差的「死画面」，且是 P1-1 的前置；**并行解码（P1-1）是不降质前提下唯一的大杠杆**，故排在核心位置。

| 阶段 | 内容 | 工时 | 预期 |
|---|---|---|---|
| P0 | 计时 + noCompress + 后台载入/进度 | 2–3 人日 | 主线程不再冻结，载入在后台可见地推进 |
| +P1-1 | 并行解码 | +1.5–2 人日 | 时长 8–12 s → **2–3 s**，音质逐字节不变 |
| +P2-1 | 分级载入 | +2 人日 | 首声 < 1 s；**已就绪音区满层** |

   与 M6-1 的「Play base 模块 ≤ 200 MB」冲突。除非上面几项仍不达标，否则不做。
4. **252 MB 常驻**：这是「不降质」的既定代价，4 GB 机型上会抬高被系统杀后台的概率。
   已按你的要求接受，不再作为可调项。
