## 0. 判据：什么才算「需要解耦」

「解耦」若没有判据，就退化成风格偏好 —— 那样会去拆一些拆了也没收益的地方，同时漏掉真正要命的地方。
本文档用四条**可检验**的判据，§3 逐条对照清单打分：

| 判据 | 要回答的问题 | 判据不满足时的后果 |
|---|---|---|
| **可测性** | 这段逻辑能不能在宿主机上验证？ | 只能靠真机与人眼。KeyboardView 那个 `fill()` 语义 bug 就是这么漏出去的 |
| **变更半径** | 改一个语义要动几处？漏一处会不会**静默**出错？ | 事件布局要动 2 处 + 2 套独立断言；策略要动 2 份实现 |
| **可替换性** | 换后端 / 换平台 / 换音源要动几处？ | M4（音色参数）、M5（MIDI 输入）接入时要回头改键盘与门面 |
| **单一事实来源** | 同一策略是否存在两份实现？ | 编辑器里调好的手感，到真机上不一致，且没人知道是哪一侧对 |

**判据之外的一律不动。** 例如「`PianoController` 有 247 行」本身不是问题；它在 §3 被列出来，是因为它同时承担编排、UI 构建、平台判断三件事，导致编排逻辑无法在宿主侧验证（判据 1）。

## 1. 全景

### 1.1 四个运行域

| 域 | 语言 | 入口 | 何时运行 |
|---|---|---|---|
| 构建期 | Python 3 + ffmpeg | `tools/` 下的脚本 | 手工执行，产出音源包与预览数据 |
| 应用启动 | C++ | `Game::init()` | 进程启动一次 |
| UI 线程 | TypeScript | `Main.scene` → `PianoController.onLoad` | 每帧 |
| **音频实时线程** | C++ | AAudio `dataCallback` → `Impl::render` | 每 4ms（48kHz / 192 帧） |

音频线程是全工程唯一有硬性约束的地方（禁锁、禁分配、禁 IO、禁 JNI，见《落地方案》§3.4）。
**本调查确认：这条约束目前守得很严** —— 回调路径只触达 `EventQueue`（消费）、`VoicePool`/`Voice`（策略与渲染）、
`SampleBank`（只读查表）、`Resampler.h`（纯 inline 函数），无锁、无堆分配、无 IO。

### 1.2 主数据流

```text
触摸 ─→ TouchRouter ──→ PianoController ──→ EventBatcher ──→ PianoEngine ─┐
         命中/力度/滑奏      编排             攒批+时间戳          门面      │
                                                                          │
   ┌──────────────────────── 原生平台 ──────────────────────────────────────┤
   ↓                                                                       │
 jsbPiano ─→ PianoBridge ─→ EventQueue ─→ Impl::render ─→ VoicePool ─→ AAudio
  (JSB)       (sebind)      (SPSC 无锁)    (事件派发)      (复音策略)    扬声器
                                                                          │
   ┌──────────────────────── 编辑器预览 ────────────────────────────────────┘
   ↓
 WebAudioEngine（AudioBufferSourceNode 变调 + GainNode 淡出）
```

两条音频路在 `PianoEngine.dispatchEvents()` 分叉。**它们读的是同一套 16 字节事件布局**，
所以 TS 侧的事件流不需要分叉 —— 这是现有设计里做得好的一处。

### 1.3 规模

| 层 | 文件数 | 行数 | 备注 |
|---|---|---|---|
| TS（`assets/scripts/`） | 11 | 2698 | 含 86 行的 `PreviewBankData.ts`（内容是一行 1MB 的 base64） |
| C++ 自研（`common/Classes/`） | 19 | 3059 | 含 `Game.*` 155 行 |
| 工具链（`tools/`） | 7 | — | Python 6 + Shell 1 |
| 测试（`tests/`） | 8 | 3326（含 cpp 测试） | TS 2 个测试文件、C++ 4 个测试程序 |

### 3.1 A 类：跨语言契约双写

| 编号 | 位置 | 现状 | 会引发的故障 | 判据 |
|---|---|---|---|---|
| A1 | `PianoEvent.h` ↔ `PianoTypes.ts` | 事件布局、枚举、`kMaxVoices`、队列容量各写一份，两侧各有一把独立的锁（C++ `static_assert` + JS 测试） | 改契约漏一侧 → **音符乱响**而非崩溃，日志查不出来 | 变更半径 |
| A2 | `SampleBank`/`VoicePool` ↔ `WebAudioEngine` | **同一策略两份实现**：选层与选根音、层内增益（±3dB 公式一致）、复音偷取（见下） | 编辑器里调好的手感在真机上不同；没人知道该信哪侧 | 单一事实来源 |
| A3 | `PianoParams.h` ↔ `ParamId` | 参数 ID 双写，注释已写明「插入中间会让已保存设置静默错位」 | 设置项串位 | 变更半径 |

**抽验结果：A1/A3 目前没有漂移。** 逐项核对一致 —— `EventType` 1..7、`EventSource` 0..2、`ParamId` 0..11、
`kMaxVoices` 64、`kEventQueueCapacity` 2048、事件 16 字节与 7 个字段偏移。
所以问题**不是「已经错了」，而是「只能靠人手同步」**：代价在下一次改契约时才显现。

A2 则**已经出现了不一致**，两处细节：

| 项 | C++ | TS 预览 |
|---|---|---|
| 力度 → 层 | `layerIndexForVelocity`：区间**包含**判定（`min ≤ v ≤ max`），表不全时退回 `v/8+1` | `pickSample`：取**层中心最近**的层。代码注释已解释理由 —— 抽取后区间之间有空隙，按包含判定会让绝大多数力度落空 |
| 层内增益 | `velocityGain`：±3dB，按区间中心归一 | `withinLayerGain`：±3dB，同上（公式一致） |
| 复音偷取 | `VoicePool::allocate`：空闲 → 释放态且包络最低 → 启动最早 | `stealVoice`：**只偷最早**，不考虑是否在释放 |

TS 侧的选层差异是**有意为之**（注释写清了原因），但它意味着「预览里听到的音色选择」并不等于真机上会做的选择；
偷取差异则是无意的行为分叉。

## 4. 解耦方案

每项给出：目标接口 / 改动面 / 验收 / 工时 / 风险。工时按 1 人日 = 6 小时有效产出。

### 第一批：低成本、直接消除「测不到」

#### T1 · `EventBatcher` 去掉 `cc` 依赖（对应 F2、C2 的一半）

- **目标**：引入两个窄接口，`EventBatcher` 不再 import `PianoEngine`
  ```ts
  interface EventSink  { available: boolean; submit(buf: ArrayBuffer, count: number): number; }
  interface AudioClock { now(): number; streamTimeMs(): number; }
  ```
- **改动**：`EventBatcher.ts`（构造注入，默认参数改为 `null` 由调用方传）、新增 `audio/AudioClock.ts`（`SystemClock` 用 `performance.now()`、`PianoEngineClock` 包原生时钟）、`PianoController` 传实例
- **不动**：事件布局、时间戳语义、`flush()` 时机
- **验收**：新增 `tests/eventbatcher.test.js`，覆盖：MIDI 钳位（**不是掩码**）、缓冲满丢弃计数、未校准时 `timeMs=0`、校准后 `timeMs = now + offset + lead`、`leadMs` 下限为 0、`reset()` 清空。`tests/run.sh` 的编译清单加入该文件

#### T2 · 视口状态机从渲染里抽出（对应 E4、B2 的一半）

- **目标**：新增 `keyboard/KeyboardViewport.ts`（纯类，零 `cc` 依赖），持有 `keyWidth`/`offsetX`/`viewportWidth`，提供
  `fitToScreen()` `scrollTo(x)` `setKeyWidth(w, anchorRatio)` `centerOn(midi)` `resetZoom()` `visibleRange()`
- **改动**：`KeyboardView` 退化为「按 layout 与 viewport 画」，把 `applyFit`/`syncViewport`/`applyScroll`/`setKeyWidth` 的数学搬进新类；`KeyboardGesture` 改为只跟 `KeyboardViewport` 对话（不再自己算 `viewportWidth`/`nodeWorldLeft`）
- **验收**：新增 `tests/viewport.test.js`，覆盖：铺满时键宽 = 视口/52、比视口窄时居中、偏移夹紧边界、**捏合缩放的锚点不动点**（缩放后锚点处的键盘内容坐标仍在同一屏幕位置）、双击复位回到铺满

#### T3 · 调试 HUD 抽出（对应 E3 的一半）

#### T4 · 后端接口化 + 事件解码独立（对应 B4、E5、C1）

- **目标**：
  ```ts
  interface AudioBackend {
      readonly kind: 'native' | 'web';
      create(): boolean; start(): boolean; stop(): void;
      submit(buf: ArrayBuffer, count: number): number;   // 原生：零拷贝交 JSB
      loadBank(mask: number): boolean; residentBytes(): number;
  ```

- **现状**：`PianoEngine::start()` 用 `device->sampleRate()` 设进 pool（正确），而 `loadBank()` 用 `_impl->sampleRate`（请求值）**再设一次**，把设备实际生效的采样率覆盖掉。AAudio 未采纳请求值时，释放斜坡时长与变调比例都会按错误采样率计算
- **改动**：`loadBank()` 改为用设备实际采样率；把「当前生效采样率」收敛成一个 getter
- **验收**：宿主测试里用一个「请求 48000、实际给 44100」的假设备断言 pool 拿到 44100
- **工时**：0.25 人日 ／ **风险**：低

## 6. 明确不做

| 不做 | 理由 |
|---|---|
| 不引入 DI 框架 / 事件总线框架 | 需要注入的点不到 6 个，构造函数传参足够；框架会让 Cocos 组件的序列化属性变得难用 |
| 不重写 C++ 内核分层 | 「契约 / 纯逻辑 / 平台」的边界已经是对的（`Resampler`/`EventQueue`/`Voice`/`VoicePool` 全宿主可测），回调约束守得很严。只拆 `Impl` 与 `SampleBank` 这两个确实过载的点 |
| 不为 TS 引入第三方测试框架（jest/vitest） | 现在用编辑器自带 `tsc` + `node`，零安装。第一批加入的测试文件沿用同一套 |
| 不做皮肤/主题系统 | 只把配色常量集中到一处（D2），够 M4 用 |
| 不把键盘渲染从单层 Graphics 改成图集/Sprite | 那是性能话题，不是解耦话题；当前 88 键只有一层 Graphics，DrawCall 不是瓶颈 |
| 不动 `Game.cpp` 的平台生命周期边 | C4 那条是**有意为之**且有代码注释论证 —— 平台事件不应交给 TS |
| 不清理 `tests/cpp/.build/` 之外的历史产物 | 已在 gitignore 内，清理与否不影响仓库 |
